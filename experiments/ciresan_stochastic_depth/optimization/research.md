# Accelerating the Ciresan-width MNIST baseline on A100

Research checked **9 September 2026** against primary PyTorch, NVIDIA and Triton sources. No paid calls or training runs were launched for this note; subsequent local CPU-only diagnostics are identified below. These are implementation recommendations and hypotheses to benchmark, not measured speedups or evidence that a candidate reaches the requested accuracy.

**Implementation update:** the [subsequent source audit](#subsequent-source-audit-and-observed-pytorch-214-compatibility-issue) records a reproduced incompatibility between the recommended new TF32 setter and an internal compiler getter. The implemented workaround uses only `torch.set_float32_matmul_precision("high")`. The user also explicitly requested tuning toward the historical official-test target; the implemented benchmark is labeled **test-monitored tuning**, superseding the validation-first recommendation below for this separate speed study.

## Recommendation

The strongest first candidate is **PyTorch 2.14.0, FP32 parameters and momentum, TF32 matmuls, GPU-resident data, and one explicit CUDA graph containing the complete fixed-shape minibatch update**. Compare fused SGD with the existing foreach SGD. Then test BF16 autocast and a compiled/autotuned implementation as separate candidates. For a short training run, eager kernels inside a CUDA graph may win total elapsed time even when an autotuned compiler wins steady-state step time. This is a workload-specific inference, not a vendor guarantee.

Preserve widths `[784,2500,2000,1500,1000,500,10]`, all six biases, and the source's hidden ReLUs. A kernel-only baseline must also preserve the source's raw-pixel scaling, output ReLU, initialization, momentum, LR, direct post-update shrinkage and example order. Removing the output ReLU, normalizing inputs, changing batch size, or changing the optimizer are legitimate optimization experiments, but separately label them as training-recipe changes. Do not compare an accelerated normalized linear-logit model against the raw-output-ReLU source and call the entire gain a kernel speedup.

## A bounded implementation ladder

1. **Eager reference:** current operation order, batch64, GPU-resident fitting tensors, no per-step `.item()` or logging. Keep an ordinary PyTorch implementation as the numerical reference. Benchmark 2.14 against 2.8 only if the older environment is already available; upgrading is not itself evidence of a speedup.
2. **Full-step graph:** capture forward, cross entropy, backward, SGD and historical shrinkage together. Static input and label buffers receive each new minibatch; graph replay uses their fixed addresses. Initially leave preprocessing/index gathering outside the graph and include its cost in the end-to-end measurement. This provides an inexpensive implementation with a clear correctness reference.
3. **Fused optimizer:** test `torch.optim.SGD(..., fused=True, foreach=False)` against foreach SGD. Do not leave `foreach=True` while adding `fused=True`. PyTorch's documented expectation is that fusion can reduce both per-parameter and per-operation overhead, but the fastest variant remains empirical. SGD does not expose Adam's `capturable` constructor option. If direct shrinkage matters, retain its exact order after the optimizer update; it is not interchangeable with `weight_decay`. [SGD 2.14 API and update definition](https://docs.pytorch.org/docs/2.14/generated/torch.optim.SGD.html).
4. **Compiler candidates:** benchmark `torch.compile(model, dynamic=False, mode="reduce-overhead")` and `mode="max-autotune"`. The latter already enables compiler-managed CUDA graphs; `max-autotune-no-cudagraphs` isolates autotuning and is the cleaner starting point when an outer explicit graph owns replay. `reduce-overhead` targets small-batch launch costs; supported capture is not guaranteed for every mutation pattern. Inspect `TORCH_LOGS=perf_hints,graph_breaks,recompiles`. A function wrapping `backward()` and `optimizer.step()` is not automatically one uninterrupted compiled graph. [Compile modes and options](https://docs.pytorch.org/docs/2.14/generated/torch.compile.html).
5. **Compile the update if useful:** a compiled optimizer or a small compiled functional SGD-plus-shrinkage update can fuse bandwidth-heavy elementwise work. The official optimizer tutorial demonstrates compiling `opt.step`; its timing example is a different model/optimizer, not a prediction here. Check momentum initialization and update order against eager SGD before using a custom fused formula. [Optimizer compilation tutorial](https://docs.pytorch.org/tutorials/recipes/compiling_optimizer.html).

The six affine layers produce multiple forward and backward GEMMs and many small auxiliary operations. NVIDIA's fully connected guide shows that small batches can be bandwidth-bound even for much larger square layers; it also emphasizes alignment and tile quantization. That supports investigating launch overhead, memory traffic and shape-specific kernels before interpreting low Tensor Core utilization as a coding error. The Ciresan dimensions are not all aligned to convenient tile widths. Compiler-internal zero padding can preserve the mathematical dimensions; changing trainable layer widths cannot. Larger batches are a separate accuracy/convergence experiment. [NVIDIA fully connected performance guide](https://docs.nvidia.com/deeplearning/performance/dl-performance-fully-connected/index.html).

## Capture and precision pitfalls that can invalidate a fast result

**Warmup is real training unless restored.** Eager warmup and compiler warmup mutate weights and optimizer state. Save the intended initial state; initialize persistent buffers; restore weights, momentum, RNG and counters before the measured run. After graph capture, restore tensor contents in place without replacing graph-referenced storage. Validate a short replay trajectory against eager execution on different batches, not repeated copies of the same batch. The setup timer must include discarded warmup work. CUDA capture requires stable shapes/addresses, side-stream warmup, no CPU synchronization inside capture, and long-lived tensors. Python data-dependent work is not replayed. [Versioned CUDA graph semantics](https://docs.pytorch.org/docs/2.14/notes/cuda.html#cuda-graphs).

**Do not mix precision-control APIs.** In 2.14 use the newer `torch.backends.cuda.matmul.fp32_precision = "tf32"` family consistently; its documentation says not to combine it with legacy `allow_tf32` settings. TF32 retains FP32 tensor storage but changes internal matmul precision. A100 has native TF32 and BF16 Tensor Core operations. [PyTorch precision controls](https://docs.pytorch.org/docs/2.14/notes/cuda.html#tensorfloat-32-tf32-on-ampere-and-later-devices), [NVIDIA Ampere tuning guide](https://docs.nvidia.com/cuda/archive/13.0.3/ampere-tuning-guide/index.html).

**BF16 is a numerical variant.** Keep FP32 master parameters and optimizer state; try `torch.autocast("cuda", dtype=torch.bfloat16)` around forward and loss, with backward outside. Do not call `.bfloat16()` on the whole model and assume AMP semantics. BF16 avoids FP16's narrower exponent range, but does not guarantee the same learned classifier. In 2.14 the AMP documentation explicitly warns that compiled backward defaults to `backward_pass_autocast="same_as_forward"`; when backward runs outside autocast, set `torch._functorch.config.backward_pass_autocast="off"` for that compiled region. Ensure loss remains FP32 and compare finite gradients and held-out quality. Autocast's weight cache must not retain stale casts across optimizer updates. [AMP 2.14 documentation](https://docs.pytorch.org/docs/2.14/amp.html).

## New kernel tools: useful candidates, not prerequisites

**cuBLASLt** supports bias-plus-ReLU epilogues, auxiliary ReLU masks, and related backward epilogues. For a custom integration, query eligible algorithms once per actual shape/layout/dtype and reuse the chosen algorithm and workspace. Heuristic queries can themselves cost tens of microseconds. Its auxiliary mask has alignment and leading-dimension requirements; supported epilogues are not a blanket promise for every dtype/layout. Start with PyTorch's existing linear kernels and compiler fusion before maintaining a custom autograd extension. [cuBLAS 13.0 epilogue and heuristic documentation](https://docs.nvidia.com/cuda/archive/13.0.3/cublas/index.html).

**Triton** provides a practical next step for a fused SGD/shrinkage update, gather/scale kernel, or a demonstrably slow matrix shape. Its official GEMM tutorial combines tiling, grouped program ordering for cache locality, masking and autotuning. A custom forward-only GEMM benchmark is insufficient: measure forward, activation gradient, weight gradient and optimizer together, and test boundary tiles such as widths2500 and500. Start with Inductor's ATen/Triton competition instead of writing all GEMMs. [Triton matrix multiplication tutorial](https://triton-lang.org/main/getting-started/tutorials/03-matrix-multiplication.html).

**CUTLASS/NVGEMM** is current, but optional. PyTorch 2.14 expands NVGEMM epilogue fusion and autotunes its candidates alongside ATen/Triton only when explicitly enabled and `nvidia-cutlass-dsl` is installed. Its release announcement specifies DSL4.6.0. PyTorch's pinned config distinguishes `CUTEDSL`, described as SM100–SM109, from `NVGEMM`; do not mistake the former for an A100 path. CUTLASS has Ampere support, but that alone does not establish that the current NVGEMM operator provider offers an eligible fast SM80 kernel for these shapes. Keep ATen/Triton fallbacks and require observed eligible candidates before spending time on this backend. No SM80 NVGEMM speedup was verified in this research. [Pinned Inductor backend configuration](https://github.com/pytorch/pytorch/blob/v2.14.0/torch/_inductor/config.py), [CUTLASS documentation](https://docs.nvidia.com/cutlass/latest/), [2.14 release announcement](https://pytorch.org/blog/pytorch-2-14-release-blog/).

## Benchmark contract for the 98.63% target

Report three clocks: **cold process-to-result** including initialization/compile/capture/evaluation; **training-loop elapsed time** with its exact included operations; and **warm steady-state time per completed optimizer update**. Synchronize at interval boundaries or use CUDA events correctly. Do not time only CPU enqueue operations. Keep candidate runs free from overlapping GPU workloads and disclose any shared CPU contention. Preserve compile-cache status: cold-cache and reused-cache timings are different results. Cache reuse is legitimate when labeled; its creation cost is not zero. [PyTorch compiler cache documentation](https://docs.pytorch.org/tutorials/recipes/torch_compile_caching_tutorial.html).

Select precision, kernels and training hyperparameters using fitting/validation data first, then freeze the candidate and official-test checkpoint schedule. On the official 10,000 examples, **98.63% means at most137 errors**. A validation score at that level does not establish the test target. If test is evaluated periodically to report time-to-target, identify the first observed qualifying checkpoint and the preceding nonqualifying checkpoint: the crossing time is bracketed by the evaluation schedule. Include evaluation/setup in the corresponding end-to-end clock, and report runs that never reach the threshold as censored. Repeated official-test-driven configuration changes turn the benchmark into test-set tuning and need that explicit limitation.

For a bounded search, first identify the fastest correct kernel path at the original batch/recipe. Then, if necessary, separately optimize batch size/LR/input/head choices to reach the accuracy threshold sooner while preserving all original widths. Fresh paired seeds distinguish a reproducible acceleration from a fortunate fast run. A fast completed run with fewer than the required accuracy is not a successful time-to-accuracy result.

## Subsequent source audit and observed PyTorch 2.14 compatibility issue

Read-only audit of `optimization/benchmark.py` and `optimization/kernels.py`, 9 September 2026. The implementation uses all 60,000 official training examples as its fitting pool and monitors the official 10,000-example test after each epoch. This is a user-requested speed-target search, explicitly separate from the interrupted validation-only stochastic-depth study. Its selected configurations and observed target crossings are not unbiased held-out generalization estimates.

### Precision API failure and tested workaround

The first 2.14 compiler attempt failed when Inductor queried `torch.get_float32_matmul_precision()` after the benchmark had set only `torch.backends.cuda.matmul.fp32_precision="tf32"`. The error's reference to mixing APIs is misleading for this reproduction: application code had used only the new setter.

Independent local CPU-only probes ran each setting in a fresh Python process using Torch2.14.0; no GPU tensors or paid calls were created:

| Setter in the fresh process | Legacy getter result | Effective CUDA precision property |
|---|---|---|
| None | `highest` | `none` |
| Backend-specific new TF32 setter | `RuntimeError` | `tf32` |
| Generic/global new TF32 setter | `RuntimeError` | `tf32` |
| Only `torch.set_float32_matmul_precision("high")` | `high` | `tf32` |

The pinned C++ source explains these results. `Context::float32MatmulPrecision` rejects effective CUDA TF32 while the older precision enum remains `HIGHEST` (lines381–395). The new general setter updates the precision map alone (lines470–482); making it global does not solve that check. `setFloat32MatmulPrecision("high")` updates both the enum and backend maps (lines440–451). The implemented fresh-process, old-API-only workaround is therefore supported by source and the independent probe. It supersedes this note's initial recommendation to use the new setter for the compiled path. Successful getter queries alone are not evidence that an entire compiler run succeeds. [Pinned PyTorch2.14 Context.cpp](https://github.com/pytorch/pytorch/blob/v2.14.0/aten/src/ATen/Context.cpp).

### Training state, graph replay and threshold audit

No critical training-state or threshold bug was found in the reviewed implementation. `BaselineStep._prepare` snapshots parameters, model buffers, gradients, SGD momentum and CPU/CUDA RNG; warms up on a side stream; and restores contents in place both before capture and in a `finally` block afterward. Persistent gradient and momentum storage remains allocated. With the required dampening0 and fresh momentum restored to zero, the first momentum update is mathematically the fresh-SGD update. This is essential: discarded warmup has not advanced the reported training trajectory.

The captured step zeros the existing gradient buffers, executes forward/loss/backward, SGD and optional source-style shrinkage, then returns a persistent device loss buffer. Each replay first copies new input/label contents into static buffers. The benchmark reads only the last minibatch loss after an epoch synchronization, so it does not accumulate aliases of that overwritten loss. Hyperparameter changes after capture are rejected. The CUDA unit tests compare changing minibatches against eager execution, check parameter/RNG restoration, and cover foreach and fused SGD. The root reported those tests passed on A100; this audit itself launched none.

Official-test evaluation uses full-precision stored parameters under TF32, including for BF16-trained variants. This is a consistent evaluation convention, and should be stated. The success check uses integer error count `<=137`, correctly representing accuracy at least98.63%. The result is the first *observed* qualifying epoch; it does not resolve the crossing within an epoch. Non-reaching attempts must remain visible.

Batch64 completes937 updates/epoch and presents59,968 examples. Batches128,256 and512 present59,904 examples per epoch. All use the60k fitting pool but discard the last incomplete shuffled batch. The recorded exposure fields correctly distinguish pool size from actual presentations. Larger-batch linear LR scaling and shrinkage `1−(1−2e−5)^(batch/64)` are explicit optimization variants: the shrinkage preserves its per-example multiplicative rate, but momentum dynamics and number of updates differ, so these are not pure kernel comparisons.

### Timing boundaries and remaining reporting issue

`optimization_app.py` starts the invocation timer before importing the benchmark. The target wall time includes that invocation's imports, claim/volume commit, dataset loading and transfers, model/optimizer creation, graph/compiler preparation, all training, shuffling, prior progress writes and test evaluation. The narrower training clock includes batch gathering, graph input copies, computation, optimizer and shrinkage; it excludes epoch permutation creation, evaluation and checkpointing. These are coherent, distinct clocks.

The threshold timestamp is taken immediately after the score is available, before writing that epoch's progress and target checkpoint; `total_run_seconds` includes those subsequent writes. Call this **time to the observed target score**, not time to the persisted final artifact. Container launch, remote dispatch/queue delay, image build and the final volume commit are outside this invocation-to-score clock and need their separate reported clocks. A reused container can also reuse imports and caches: do not describe every invocation as a cold process unless freshness is established. The repeated-single-batch microbenchmark is labeled a kernel test, not a convergence result.

One result-field issue was sent to the root: `final_test` is assigned the last saved history score, even if a later epoch diverges before evaluation. In that branch it describes an earlier model, not the final diverged weights. Reports should call it `last_evaluated_test` or leave final quality unset for a diverged run, and retain the divergence flag. No source files were edited by this audit.
